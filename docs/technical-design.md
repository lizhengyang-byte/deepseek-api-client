# DeepSeek API 版 · 技术设计文档

本文档描述「DeepSeek API 版」客户端的技术方案：如何用官方账号接入、如何按 API 计费、如何把官方导出的数据完整还原为可继续对话的会话、如何把界面还原到与 DeepSeek 官方 App 一致的观感、如何以最小代价补一项联网检索能力，以及如何把同一套代码交付成安卓 APK。文档面向参与开发与评审的工程师，读完后应能判断架构是否可行、边界是否清楚、风险是否可控。

## 方案结论与范围

### 一句话方案

采用 **纯前端 + 本地优先** 的单页应用：React + TypeScript 构建界面，对话数据全部存在本地 IndexedDB 中，模型能力通过 **OpenAI 兼容的 DeepSeek 官方 API** 直连，按官方 API 余额计费；同时提供一条实验性的「网页会话令牌」通道，用于没有 API Key 时以官方网页账号登录。官方导出的数据包在本地解析、归一化后写入同一个会话库，历史消息与新建消息共用一套数据结构，因此「导入即可续聊」。在这个底座上只增加一层**极简 Agent**：一个 `search_web` 工具、最多一次检索、失败即降级，不做规划与工具循环。同一份前端产物再用 **Capacitor 6** 封装为安卓 APK，并通过一个自写原生插件补上「App 内登录官方账号」这一平台独有能力。

### 关键决策

| 决策点 | 选择 | 理由与代价 |
| --- | --- | --- |
| **数据存放位置** | 浏览器 / WebView 的 IndexedDB，全量本地 | 不上传服务器，隐私成本最低、可离线浏览历史；代价是多端同步需要自己导出/导入，清理数据会丢库。 |
| **模型接入方式** | 官方 API（优先）+ 网页令牌通道（实验） | API 通道稳定、可计费、有明确的错误码；网页通道依赖非公开接口，随时可能变动，作为降级手段而非主路径。 |
| **交付形态** | Web 静态站点 + 安卓 APK，共用同一套代码 | 用户要的是能装在手机上的 App；Capacitor 包一层 WebView 即可复用全部业务代码，代价是多一个原生工程与签名环节。 |
| **导入数据形态** | 解析官方导出包，归一化为统一消息模型 | 不重建「像官方」的临时视图，而是直接落库；导入后的会话与原生会话权限、操作完全一致。 |
| **界面还原粒度** | 布局、间距、圆角、配色、交互节奏 1:1 对齐；品牌素材不使用官方 Logo 与图标资源 | 能保持「就是这个 App」的熟悉感，同时不复制官方商标与受版权保护的图形资源，降低开源分发风险。 |
| **凭证输入方式** | 单一输入框 + 形态识别 + 原生登录插件 | 用户不为「先选哪个 tab」付出认知成本；插件能自动取回令牌，减少手工翻 Local Storage，但只在 App 内可用，Web 端优雅降级。 |
| **数据导入入口** | 本地文件与下载链接双入口，共用一条解析管线 | 链接导入减少「先下载再找文件」的动作；链路只在取文件这一段不同，后续解析、预览、写库完全复用，避免两套逻辑走偏。 |
| **Agent 深度** | 一个工具、最多一次检索、无规划无循环 | 纯前端没有服务端跑长任务，多一步就多一次等待与一次计费；多数问题不需要检索，所以把能力做浅反而更贴官方体验。 |

### 范围边界

- **本次交付**：会话列表与对话主流程、流式输出、深度思考内容折叠、会话搜索与重命名、官方导出包导入与续聊、用量与费用估算、设置项、明暗主题、移动端适配、最小 Agent（联网搜索）、安卓 APK 与 App 内登录。
- **不在本次内**：多端云同步服务端、团队协作与分享、图片/文件上传解析、语音输入、私有化模型接入、多步任务规划与多工具编排。这些在架构上预留了扩展点（见「演进路线」）。

## 系统架构

### 分层结构

整体分为四层，层间只通过明确定义的接口通信，便于把「传输通道」单独替换而不影响界面与数据。

| 层 | 职责 | 主要实现 |
| --- | --- | --- |
| **视图层** | 页面结构、会话列表、消息渲染、输入框、设置页；不含网络与存储逻辑 | React 组件 + Tailwind |
| **状态层** | 会话/消息的增删改、流式片段合并、检索调度、当前选中会话、UI 开关 | Zustand store |
| **领域层** | 消息上下文裁剪、导入归一化、检索与降级、用量与费用计算、导出、凭证形态判定 | 纯函数模块 |
| **基础设施层** | IndexedDB 读写、官方 API 与网页通道、搜索接口、密钥加解密、原生登录插件桥接 | Dexie / fetch / WebCrypto / Capacitor 插件 |

### 运行形态

- **浏览器 Web 应用**：静态站点托管，无后端，能力最全（除 App 内登录）。
- **安卓 APK**：Capacitor 6 包一层 WebView，业务代码零改动，`androidScheme` 设为 `https`，WebView 的 origin 为 `https://localhost`，官方接口回显该 Origin，因此仍可直连 fetch 并保留 SSE 流式。
- **原生能力边界**：App 内登录依赖一个自写的 Capacitor 插件（`WebLoginPlugin`），这是唯一一处平台差异；Web 端检测不到插件时自动隐藏该入口，退化为粘贴令牌。
- CORS 说明：DeepSeek API 支持跨域直连；若部署环境被中间层拦截，可在设置中填写自建反向代理地址作为基址。联网检索同样受 CORS 约束，搜索接口需允许跨域。

## 技术选型

| 能力 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | React 18 + TypeScript 5 + Vite 5 | 流式更新频繁，需要细粒度重渲染控制；Vite 提供秒级冷启动，产物为纯静态文件。 |
| 样式 | Tailwind CSS 3 + CSS 变量 | 用设计令牌统一颜色与圆角，明暗主题只切换变量；避免为了「像」而复写大段 CSS。 |
| 状态 | Zustand | 比 Context 更少的重渲染，不需要 Provider 嵌套；store 可被非 React 代码调用。 |
| 本地库 | Dexie 4（IndexedDB） | 提供索引、事务与版本迁移；单库可容纳数十万条消息，避免 localStorage 的 5MB 限制。 |
| 消息渲染 | react-markdown + remark-gfm + rehype-katex + highlight.js | 表格、公式、代码高亮是编程问答的高频场景；渲染结果用 memo 缓存，避免流式时整段重排。 |
| 解压 | JSZip | 导出包在本地解压，全程不上传。 |
| 封装 | Capacitor 6 | 同一套前端产物直接装进安卓 WebView，插件机制支撑原生登录能力。 |
| 图标 | lucide-react | 线条风格与官方观感接近，且为开源许可，不引入官方图形资源。 |

## 数据模型与本地存储

### 实体定义

| 实体 | 关键字段 | 约束 |
| --- | --- | --- |
| Conversation | id、title、createdAt、updatedAt、model、pinned、archived、source、messageCount | id 优先沿用官方导出中的原始 id，保证重复导入可幂等去重；source 标记 native / imported。 |
| Message | id、conversationId、role、content、reasoning、status、tokens、createdAt、parentId | 一条消息一条记录；流式期间 status 为 streaming，结束后落盘为 done，异常为 error。 |
| Setting | key、value | 单行键值表，含模型、采样参数、主题、代理基址、价格表、检索接口配置。 |
| UsageLog | id、conversationId、model、promptTokens、completionTokens、cost、at | 用于费用估算与趋势展示，按天聚合查询。 |

### 库结构与迁移

```typescript
db.version(1).stores({
  conversations: 'id, updatedAt, pinned, archived, source',
  messages: 'id, conversationId, createdAt, [conversationId+createdAt]',
  settings: 'key',
  usage: '++id, at, conversationId',
});

db.version(2).stores({
  messages: 'id, conversationId, createdAt, [conversationId+createdAt], status',
});
```

消息按 `[conversationId+createdAt]` 建复合索引，打开会话时只读当前会话的连续区间，避免全表扫描。版本升级用 Dexie 的 **version().upgrade()** 做字段补齐，不删除用户数据。

### 容量与清理

- 单条消息正文按字符计，10 万条消息约 200–400 MB，接近浏览器配额上限，因此提供「按时间归档」与「导出后清理」两个入口。
- 启动时用 **navigator.storage.estimate()** 读取已用配额，占用超过 70% 时在设置页提示导出备份。
- 持久化申请：调用 **navigator.storage.persist()**，降低被系统回收的概率。

## 认证与鉴权

### 凭证形态与自动分流

登录页不再让用户先选通道，而是 **先识别、再分流**。识别是纯本地判断（`src/lib/credential.ts`），不发请求：

| 形态 | 判定规则 | 校验动作 | 计费与额度 | 稳定性 |
| --- | --- | --- | --- | --- |
| **API Key（主）** | `^sk-[A-Za-z0-9_-]{12,}$` | `GET /user/balance`，401 直接拒绝入库 | 走 API 余额，可查余额、可估算单次费用 | 官方公开接口，契约稳定 |
| **网页令牌（实验）** | 三段式 JWT，或长度 ≥40 且字符集受限的单串 | `POST /api/v0/chat_session/create` 真实建一次会话 | 走网页账号额度，不产生 API 账单 | 依赖非公开接口，随官方改版可能失效 |

输入清洗：自动去掉 `Authorization:` / `Bearer ` 前缀与包裹引号，避免用户整行复制粘贴后校验失败。识别结果为 `unknown` 时只报错、不写库。

分流后两条通道都调用已有的登录动作，区别只在「校验接口」与「发消息时的 Transport 实现」，不存在绕过校验的入口。

### App 内登录（原生插件）

Web 端无法读到 `chat.deepseek.com` 的 localStorage（跨域），因此该能力放在原生侧：

```text
用户点「在 App 内登录官方账号」
  → JSBridge: WebLogin.login()
  → 原生弹出 Dialog + WebView，加载 https://chat.deepseek.com/sign_in
  → 每次 onPageFinished 注入轮询脚本，读取 localStorage['userToken' | 'token']
  → 命中后通过 @JavascriptInterface(DSBridge.post) 回传字符串
  → 原生关闭 Dialog，resolve 插件调用返回 { token }
  → 前端拿着 token 走与手工粘贴完全相同的 loginAuto() 校验与落库
```

设计约束：

- **只搬运令牌**，不读取、不提交任何账号密码；登录表单完全由官方页面渲染。
- 只在官方域名下加载，地址写死，不接受调用方传入 URL，避免被当作任意网页容器。
- 用户按返回键随时取消，返回 `{ cancelled: true }`，前端保持未登录状态。
- 令牌有效性与手工粘贴通道共用同一段校验代码，不存在「插件路径绕过校验」。
- 插件源码放在 `native/android/`，由 `scripts/android-patch.mjs` 幂等注入到 `cap add` 生成的原生工程，因此仓库不必提交整个 `android/` 目录。

两条通道在领域层被抽象为同一个 **Transport** 接口，只有 `send()` 的实现不同，界面与数据层不感知通道差异。两种凭证都存在时默认用 API Key，可在设置页显式切换。

### 密钥本地加密

绝不把明文密钥写进 localStorage。首次写入时用 WebCrypto 生成不可导出的 AES-GCM 密钥，存于 IndexedDB 的非导出句柄；密文与随机 IV 一并保存。读取只在发起请求前解密到内存变量，不写入状态持久层。

```typescript
const key = await crypto.subtle.generateKey(
  { name: 'AES-GCM', length: 256 },
  false,                       // 不可导出
  ['encrypt', 'decrypt']
);
const iv = crypto.getRandomValues(new Uint8Array(12));
const cipher = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv }, key, new TextEncoder().encode(apiKey)
);
```

### 凭证校验与失效处理

- 保存前调用 **GET /user/balance** 做一次轻量校验，返回 401 直接提示「密钥无效」，不写入库。
- 运行中遇到 401：清空内存凭证、保留密文并标记为 invalid，界面切到登录页，提示「密钥已失效或被删除」。
- 网页令牌遇到 401/403：提示「网页会话已过期，请重新登录」，并保留 API Key 通道的可用性。

### 安全清单

- 所有请求只发往官方域名、用户自填的代理基址与用户自己配置的搜索接口，不做任何第三方上报。
- 不记录请求头到日志；调试日志默认关闭，开启时对密钥做掩码。
- 导出文件由用户主动触发，导出内容不含密钥、令牌与搜索接口密钥。
- README 与首次启动页明确提示：本项目为非官方客户端，密钥仅存于本机，泄露风险由使用者自担。

## 最小 Agent 设计（联网搜索）

### 定位

只补一项能力：**需要时让模型查一次网**。不做多步规划、不做工具循环、不做并行工具、不做子 Agent。约束来自两条：应用是纯前端，没有服务端承载长任务；每多一次工具往返都要消耗用户自己的 API 余额。

### 实现结构

| 模块 | 职责 |
| --- | --- |
| `src/lib/agent.ts` | 工具定义 `search_web`、检索调度 `decideSearch`、接口适配 `fetchSearch`、结果压缩 `runSearch` |
| `src/store/chat.ts` | 组装上下文前插入调度与检索，把资料块作为 `system` 前置，来源列表追加到答案末尾 |
| `src/components/SearchDialog.tsx` | 接口配置面板：类型 / 地址 / 密钥三字段 |
| `src/components/Composer.tsx` | 输入栏「联网」开关；未配置时点击即唤起配置面板 |
| `src/store/settings.ts` | `searchEnabled` / `searchProvider` / `searchEndpoint` / `searchKey` 持久化 |

### 一轮回答的调用序列

1. `POST /chat/completions`（非流式，`deepseek-chat`，`tools=[search_web]`，`max_tokens=128`，`temperature=0`）→ 期望得到 `tool_calls[0].function.arguments.query`；
2. 若得到查询词，调用用户配置的搜索接口，取前 5 条，每条标题 + URL + 260 字摘要；
3. `POST /chat/completions`（流式，用户当前模型）→ 资料块以 `system` 前置，其余为正常上下文。

调度固定使用 `deepseek-chat` 而不是当前模型：`deepseek-reasoner` 不支持工具调用，用它做调度会稳定失败并多花一次推理费用。

### 失败与降级

| 情况 | 处理 |
| --- | --- |
| 调度请求非 2xx / 解析失败 / 未发起工具调用 | 视为「不需要搜索」，直接走第 3 步 |
| 搜索接口非 2xx、CORS 被拒、结果为空 | 丢弃资料块，toast 提示原因，继续普通作答 |
| 用户在调度中途停止生成 | `AbortSignal` 一并传给两次 fetch，消息标记为已停止 |

所有降级路径都不抛给上层，保证「搜索不可用」永远不会把一次正常提问变成失败。

### 边界与取舍

- 只在 API Key 通道生效；网页令牌通道使用官方会话接口，无法注入外部资料，因此跳过调度。
- 检索结果不落库，仅作为本次请求的临时资料；来源链接随答案一起存进消息正文，便于回溯。
- 结果条数与摘要长度是硬上限，避免检索一次就把上下文和费用顶满。
- 不引入 embedding / 本地知识库 / 向量检索，这些问题用「多问几轮」解决比加一套管线更划算。

## 对话链路

### 请求构造

发送时从当前会话取最近若干轮消息，转换为官方接口的 **messages** 数组；系统提示词优先使用会话级设置，其次全局设置。历史裁剪按 token 预算而非条数：从最新往旧累计，超出预算即停止，并保证首条为 system。

```typescript
POST https://api.deepseek.com/chat/completions
{
  "model": "deepseek-chat",        // 或 deepseek-reasoner
  "messages": [{ "role": "user", "content": "..." }],
  "stream": true,
  "temperature": 0.7,
  "max_tokens": 4096
}
```

### 流式解析

用 fetch + ReadableStream 手动切 SSE，而不是 EventSource：EventSource 不支持 POST 与自定义请求头。逐块解码后按行缓冲，遇到空行视为一条事件结束，取 **data:** 后的 JSON；**[DONE]** 结束循环。

- 正文增量写入 **delta.content**，思考增量写入 **delta.reasoning_content**，两条通道分别累积，避免思考内容混进最终回答。
- 每收到片段只更新当前消息的内存缓冲，**节流 100ms** 批量提交到 store，降低重渲染次数。
- 流结束或用户点「停止」时统一落库一次，写入最终正文、token 用量与状态。
- 异常中断（网络断开）保留已生成内容，状态置为 interrupted，允许「继续生成」。

### 思考内容的呈现

深度思考模式下，回答上方出现可展开区域，标题为「已深度思考」，展开后按段落呈现推理过程，默认折叠。折叠状态不写入数据库，仅作为组件内部状态，避免污染数据。

### 重试与错误码

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 401 | 密钥无效 | 清空内存凭证，跳登录页，不自动重试 |
| 402 | 余额不足 | 提示余额不足并给充值入口链接，停止发送 |
| 429 | 限流 | 指数退避重试 2 次（1s、3s），仍失败则提示稍后再试 |
| 5xx | 服务端异常 | 保留草稿，支持一键重发 |

### 用量与费用

官方在流式最后一帧返回 usage（含 prompt_tokens、completion_tokens）。若某次请求未返回，则用本地启发式估算（中文按 1 字≈0.6 token、英文按 4 字符≈1 token）并在界面标注「估算」。费用按可配置价格表计算，设置页允许用户按官方最新价格自行调整，默认值只作示例。开启联网时，调度那一次小请求的用量不计入本条消息统计（它是内部行为，不是一次对话回合）。

## 官方数据导入与续聊

### 导出包形态

官方数据导出通常是一个压缩包，内含一份记录全部会话的 JSON。不同版本的文件名与外壳字段会变，因此解析器不绑定文件名，而是**按结构识别**：遍历所有 JSON 文件，寻找同时满足「可枚举出会话对象」与「会话内含消息集合」的节点。

### 归一化策略

把三种常见结构收敛到同一个中间形态：

1. **mapping 树**：会话内以节点字典表示，节点含 parentId 与 message，需从叶子回溯到根，还原出线性对话；分支时取当前选中的叶子。
2. **messages 数组**：每条含 role 与 content，按时间或数组顺序直接映射。
3. **chat_messages 数组**：字段名不同（如 content 为对象或数组），需提取文本片段拼接。

```typescript
type RawConversation = Record<string, unknown>;
interface NormalizedMessage {
  role: 'user' | 'assistant' | 'system';
  content: string;
  reasoning?: string;
  createdAt: number;
}
// 入口对任意输入都返回 NormalizedMessage[]，保证下游只有一种形态
```

### id 与时间

- 会话 id 尽量沿用原始 id；缺失时用「标题 + 首条消息时间」做稳定哈希，保证多次导入不产生副本。
- 时间戳兼容秒/毫秒/ISO 字符串三种写法，统一转为毫秒；无法解析时按导入顺序递增补齐。
- 消息 id 用「会话 id + 序号」派生，续聊产生的新消息用随机 id，避免与导入数据冲突。

### 导入流程

两个入口在「拿到 File 对象」之后合并为同一条管线：

| 入口 | 取文件方式 | 失败处理 |
| --- | --- | --- |
| 本地文件 | 拖拽 / 文件选择器 | 解析失败时回填解析器给出的原因 |
| 下载链接 | `fetch(url, { credentials: 'include' })` → `Blob` → `File` | 按 CORS / 401-403 / 404 / 内容过小分别给出可执行提示 |

1. 取文件：压缩包在本地用 JSZip 解压，全程不上传。
2. 解析：`parseExportFile` 产出归一化结果，界面展示「会话数 / 消息数 / 跳过数」预览，用户确认后才写入。
3. 写入：单事务完成，遇到同 id 会话按「消息并集」策略合并，保留本地更长的分支。
4. 收尾：自动定位到最新会话，可直接在输入框续聊。

链接导入的三个实现细节：

- 请求带 `credentials: 'include'`，让需要登录态的导出链接在 WebView / 浏览器里带上 cookie；跳转自动跟随（官方链接常见 302 到对象存储），跨域被拒时给出「需要登录 cookie，请先下载再选本地文件」的明确指引。
- 大小上限 200MB，超出直接拒绝，避免移动端内存被拖垮。
- 响应体小于 1KB 视为异常（常见于链接被重定向到登录页），提示用户检查链接而非静默解析。

### 续聊的上下文策略

导入的历史消息与本机新消息同库同结构，续聊时无需特殊处理。为控制成本，默认只回传最近 **N** 轮（默认 20 轮，可在设置调整），并对超长单条消息做尾部截断，截断处在界面提示「历史已裁剪」。若用户希望严格延续早期上下文，可在会话设置中改为「全量回传」。

### 页面结构

- **欢迎页**：居中标题、一句引导、四枚建议胶囊、底部悬浮输入框；不显示空会话列表。
- **会话页**：顶部细导航（返回/标题/更多），消息区单列最大宽度约 760px，用户消息右侧浅灰气泡，助手消息无气泡直接排版。
- **侧栏**：分组按「今天 / 近 7 天 / 更早」，每项单行省略，悬浮出现重命名与删除。
- **输入区**：圆角容器包裹多行输入、左侧附件按钮与「联网」开关、右侧发送/停止按钮；空内容时按钮为禁用灰，输入后变品牌蓝。

### 交互细节

- 发送后输入框清空并保留草稿历史，向上箭头可调回上一条输入。
- 消息悬浮出现「复制 / 重新生成 / 删除」，移动端常显，避免只有悬停才可见。
- 流式期间底部显示「停止生成」，点击立即中止并保留已输出内容。
- 滚动遵循「贴底才自动跟随」：用户上滑查看历史时不被强制拉回。

### 响应式与主题

宽度小于 768px 时侧栏转为抽屉，顶部出现汉堡按钮；输入区固定在安全区上方并适配 **env(safe-area-inset-bottom)**。主题通过 **data-theme** 切换 CSS 变量，跟随系统或手动指定，选择结果写设置表。

### 测试策略

- **解析器单测**：用三套脱敏样例覆盖 mapping、messages、chat_messages 三种结构，断言消息条数、角色序列与时间递增。
- **SSE 单测**：构造分块到达的字节流（含跨块断行、中文多字节），断言正文与思考内容拼接正确。
- **凭证与链接单测**：`sk` / JWT / 超长串的形态判定、`Bearer` 清洗、空与 unknown、链接协议校验。
- **端到端**：手工路径清单——首次登录（粘贴与 App 内登录）、发消息、停止、重发、导入（本地与链接）、续聊、刷屏后数据仍在、清除密钥。
- **检索降级**：手工验证「未配置搜索接口」「接口 401」「接口不含 CORS」三种情况的降级路径，确认仍能正常作答。

## 风险与合规

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 接口变更 | 网页通道接口调整导致 404 或结构变化 | 通道隔离 + 明确错误提示 + 一键切回 API；README 标注实验性 |
| 官方登录页存储变动 | 插件读不到 `userToken` | 提示改用手工粘贴；两条路径共用同一段校验，不静默失败 |
| 导出链接失效/跨域 | 链接导入报 CORS / 401 / 403 | 分类提示 + 引导改本地文件；200MB 上限避免内存崩溃 |
| 搜索接口跨域被拦 | 检索全部失败，答案没有来源 | 降级为普通对话并提示原因；文档给出 SearXNG 开 CORS 与自建反代两种方案 |
| 检索带来额外费用 | 每次提问多一次调度调用 | 调度限制 `max_tokens=128`、温度 0，且只在用户显式开启时发生 |
| 密钥泄露 | 本机被他人使用或恶意脚本读取 | AES-GCM 加密存储、不可导出密钥、支持一键清除、不在日志中出现 |
| 商标与素材 | 使用官方 Logo、图标、字体造成侵权 | 不使用官方图形资源，图标全部来自开源图标库；README 注明非官方、无关联 |
| 数据丢失 | 用户清理数据或卸载 App | 导出为 JSON、导入同一格式、设置页常驻备份提示 |
| 计费争议 | 本地估算与官方账单不一致 | 费用一律标注「估算」，真实账单以官方控制台为准 |

### 未验证项

App 内登录插件已编入安装包，但未在真机 / 模拟器上实测（构建环境无 KVM，无法跑模拟器）。官方登录页是否仍将令牌写入 `localStorage['userToken']`，需要真机验证；若官方改动，插件会读不到令牌，此时手感退化为手工粘贴，不影响主路径。联网检索同样只在本机拦截与手工路径下验证过接口约定，真实第三方搜索服务的返回结构需在配置后实测。

## 演进路线

- **一期**：API 通道完整功能、导入与续聊、界面还原、本地加密。
- **二期**：最小 Agent（联网搜索）、网页通道稳定性、附件与图片问答、提示词库、快捷键。
- **三期**：可选自建同步服务（端到端加密）、多设备增量合并、插件式模型适配器。

> Agent 方向不做扩张：新增能力前先回答「它会不会让一次普通提问多花一轮请求」，否则不做。
